# Flood Example Report

This document explains the `examples/flood/` example in the Commonware monorepo. The example is a symmetric peer-to-peer workload generator: every deployed node runs the same binary, discovers other nodes, continuously sends random messages to all connected peers, and records receive latency.

## High-Level Purpose

The flood example is designed to stress the Commonware networking stack in a realistic distributed deployment. It does not implement a higher-level protocol like consensus or replication. Instead, it focuses on:

- discovering peers across regions,
- establishing authenticated encrypted connections,
- sending application data at high rate,
- measuring one-way delivery latency,
- exporting metrics to a monitoring stack.

The main binary is [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs). The setup and deployment artifacts are generated by [examples/flood/src/bin/setup.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/setup.rs).

## Main Participants

There are three practical participant types in this example.

### 1. Flood peers

These are the actual EC2 instances running the `flood` binary. Every flood peer has the same role and behavior.

Each peer:

- loads the shared `hosts.yaml` inventory,
- loads its own private key from its config file,
- derives its public key,
- starts a Tokio-based Commonware runtime,
- starts the authenticated discovery network,
- continuously sends messages,
- continuously receives messages and records latency.

This logic starts in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L34).

### 2. Bootstrappers

Bootstrappers are not a separate service. They are ordinary peers selected during setup to seed discovery.

The setup binary randomly chooses some generated peer identities as bootstrappers in [examples/flood/src/bin/setup.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/setup.rs#L117). At runtime, each peer converts the configured bootstrapper public keys into socket addresses using the shared host inventory in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L116).

Their role is only to help new peers join the network. After startup, they behave like all other peers.

### 3. Monitoring instance

The AWS deployer provisions a separate monitoring instance. Its private IP is stored in `Hosts.monitoring` in [deployer/src/aws/mod.rs](/Users/dhruv/Documents/monorepo/deployer/src/aws/mod.rs#L556).

The flood peers use this monitoring address for optional trace export in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L77), while Prometheus metrics are exposed locally for scraping on `:9090` in [runtime/src/tokio/telemetry.rs](/Users/dhruv/Documents/monorepo/runtime/src/tokio/telemetry.rs#L35). This monitoring node is not on the application data path. It exists to collect metrics, logs, traces, profiles, and dashboards.

## Peer Startup Flow

Each flood peer performs the following steps.

### 1. Load host inventory

The binary reads `--hosts`, parses it as `commonware_deployer::aws::Hosts`, then converts each host name from hex into an Ed25519 public key. This builds a `HashMap<PublicKey, IpAddr>` in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L42).

This is how the peer learns:

- all peer identities,
- all peer public IP addresses,
- the monitoring IP.

### 2. Load local identity

The binary reads `--config`, parses the YAML into the flood `Config`, decodes the private key, and derives its public key in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L56).

### 3. Start runtime and telemetry

The example uses `commonware_runtime::tokio` as its production runtime. The runtime is initialized with a configurable worker thread count in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L68).

The runtime module is described in [runtime/src/tokio/mod.rs](/Users/dhruv/Documents/monorepo/runtime/src/tokio/mod.rs#L1).

Telemetry is initialized with:

- JSON structured logging,
- Prometheus metrics exposed on `METRICS_PORT` at `/metrics`,
- optional trace export to the monitoring instance.

This happens in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L77).

### 4. Build bootstrapper list

The peer turns configured bootstrapper public keys into `(PublicKey, SocketAddr)` pairs using the shared peer IP map in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L110).

### 5. Start discovery network

The binary creates a `commonware_p2p::authenticated::discovery::Config::local(...)` in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L127).

That config includes:

- the local signing key,
- an application namespace,
- the local listen address,
- the local dialable address,
- the bootstrapper list,
- the maximum message size.

The example uses the `local` profile from [p2p/src/authenticated/discovery/config.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/config.rs#L168), which intentionally favors fast peer discovery over conservative production defaults.

### 6. Register the authorized peer set

The peer calls `oracle.track(0, peer_keys)` in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L142).

This is the critical application-level input to the discovery module. The discovery protocol assumes peers agree on the composition of a tracked peer set for a given index. In this example:

- there is one tracked set,
- its index is `0`,
- it contains all deployed peers.

The manager API that supports this is defined in [p2p/src/lib.rs](/Users/dhruv/Documents/monorepo/p2p/src/lib.rs#L246).

### 7. Register one application channel

The flood example registers channel `0` with a very high quota and configurable backlog in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L145).

The send/receive traits and recipient model are defined in [p2p/src/lib.rs](/Users/dhruv/Documents/monorepo/p2p/src/lib.rs#L31).

## Communication Architecture

The communication path has several layers.

### Layer 1: Application behavior

The flood application itself has only two application tasks:

- `flood_sender`
- `flood_receiver`

The sender generates messages forever. The receiver consumes delivered messages forever.

There is no request/response pattern, no reliability layer, no sequencing, and no application acknowledgement.

### Layer 2: P2P discovery network

The application does not manage raw sockets directly. It uses `commonware_p2p::authenticated::discovery`, documented in [p2p/src/authenticated/discovery/mod.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/mod.rs#L1).

This module provides:

- authenticated peer identities,
- peer-set based authorization,
- automatic peer discovery,
- multiplexed message channels,
- per-channel rate limiting,
- routing of application payloads to connected peers.

Internally, the discovery network starts several actors in [p2p/src/authenticated/discovery/network.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/network.rs#L142):

- `tracker`
- `router`
- `spawner`
- `listener`
- `dialer`

These actors divide the network responsibilities.

#### Tracker

The tracker manages:

- tracked authorized peer sets,
- bootstrapper information,
- known ingress information for peers,
- retry and blocking policy,
- address freshness and gossip-related metadata.

See [p2p/src/authenticated/discovery/actors/tracker/mod.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/tracker/mod.rs#L1).

#### Listener

The listener accepts inbound connections, applies handshake throttling, filters disallowed private IPs when configured, and hands successful connections off to the rest of the network. See [p2p/src/authenticated/discovery/actors/listener.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/listener.rs#L1).

#### Dialer

The dialer periodically tries to connect to bootstrappers and discovered peers. It resolves ingress addresses, enforces dial pacing, and establishes outgoing encrypted streams. See [p2p/src/authenticated/discovery/actors/dialer.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/dialer.rs#L1).

#### Spawner and peer actors

The spawner creates per-peer actors for established connections. The per-peer actor is responsible for the ongoing exchange of discovery payloads and application data over a live connection. See:

- [p2p/src/authenticated/discovery/actors/spawner/mod.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/spawner/mod.rs#L1)
- [p2p/src/authenticated/discovery/actors/peer/mod.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/peer/mod.rs#L1)

#### Router

The router maintains the set of currently connected peers and forwards application data to them. Its `Recipients::All` handling explicitly iterates only over active connections in [p2p/src/authenticated/discovery/actors/router/actor.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/router/actor.rs#L138).

This means the flood sender does not send to every authorized identity unconditionally. It sends only to the subset of peers with live connections at that moment.

### Layer 3: Encrypted stream transport

The discovery network runs over `commonware_stream::encrypted`, not directly over unframed plaintext sockets. This transport is documented in [stream/src/encrypted.rs](/Users/dhruv/Documents/monorepo/stream/src/encrypted.rs#L1).

This layer provides:

- authenticated handshake,
- encrypted framing,
- mutual identity verification,
- forward secrecy,
- handshake timeout,
- transcript-bound session derivation.

The stream documentation states that it uses:

- an ephemeral X25519 Diffie-Hellman exchange,
- ChaCha20-Poly1305 for message encryption,
- transcript binding to prevent replay and transcript substitution.

See [stream/src/encrypted.rs](/Users/dhruv/Documents/monorepo/stream/src/encrypted.rs#L12).

## Discovery Communication

The discovery protocol is the control plane for the example.

Its behavior is explained directly in [p2p/src/authenticated/discovery/mod.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/mod.rs#L16).

### Shared peer-set assumption

The protocol assumes all peers agree on the ordered composition of peer set `0`. Because all peers track the same set, they can interpret discovery metadata consistently.

### `BitVec` gossip

Each peer periodically sends `BitVec` messages that summarize which peers in the tracked set it currently knows how to dial. These are small periodic discovery messages and also serve as keep-alive traffic.

### Signed `Info` gossip

If one peer knows dialable address information that another peer lacks, it sends signed `Info` records in a `Peers` payload. Each `Info` includes:

- ingress address,
- timestamp,
- public key,
- signature over ingress and timestamp.

These payload types are defined in [p2p/src/authenticated/discovery/types.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/types.rs#L62).

### Greeting after connection

After a connection is established, peers exchange a greeting containing their own signed address information. This helps correct stale peer-address knowledge quickly.

## Application Data Communication

The data plane for the example is intentionally simple.

### Outgoing messages

The sender task in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L156):

- allocates a message of `config.message_size`,
- writes the current timestamp into the first 8 bytes,
- fills the remaining bytes with random data,
- sends the payload to `Recipients::All`,
- marks the send as `priority = true`,
- increments a sent-message counter.

The message contents are:

- bytes `0..8`: `u64` send timestamp in little-endian form,
- bytes `8..`: random filler.

The message has no other structure.

### Incoming messages

The receiver task in [examples/flood/src/bin/flood.rs](/Users/dhruv/Documents/monorepo/examples/flood/src/bin/flood.rs#L179):

- waits on `flood_receiver.recv()`,
- ignores payloads shorter than 8 bytes,
- decodes the first 8 bytes as the send timestamp,
- compares that timestamp to local current time,
- records the observed latency into a histogram.

This is a one-way latency estimate, not a round-trip measurement.

### Channel multiplexing

Application data sent over discovery is wrapped in `Payload::Data`, whose inner `Data` structure contains:

- `channel: u64`
- `message: IoBuf`

That structure is defined in [p2p/src/authenticated/data.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/data.rs#L5). In flood, the application uses only channel `0`.

### Send semantics

The `Sender` trait in [p2p/src/lib.rs](/Users/dhruv/Documents/monorepo/p2p/src/lib.rs#L155) makes several behaviors explicit:

- offline recipients are skipped,
- successful send does not guarantee delivery,
- rate-limited peers may be skipped,
- validation errors like oversize messages are reported.

The channel implementation also enforces a maximum message size before handing data to the router in [p2p/src/authenticated/discovery/channels.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/channels.rs#L21).

## Important Behavioral Properties

The flood example has a few properties worth making explicit.

### It is a mesh workload

Every peer is both a sender and a receiver. There is no coordinator, no server tier, and no client tier.

### Bootstrappers are temporary discovery aids

They are only the first connection targets. They do not remain a logically distinct component of the protocol.

### `Recipients::All` means all connected peers

It does not mean all authorized peers whether connected or not. The router sends only to the peers with currently active relays in [p2p/src/authenticated/discovery/actors/router/actor.rs](/Users/dhruv/Documents/monorepo/p2p/src/authenticated/discovery/actors/router/actor.rs#L138).

### Delivery is best-effort

The p2p sender API explicitly allows offline peers to be skipped and does not guarantee message delivery after a successful send call. That is acceptable here because the example is a stress benchmark, not a reliable messaging system.

### Measured latency is one-way and local-clock based

The receiver subtracts the embedded send timestamp from its own local current time. This assumes clock skew is limited enough that the measurement is useful. It is not a round-trip time measurement and does not correct for clock offset.

### The example intentionally minimizes protocol complexity

Flood does not implement:

- retransmission,
- acknowledgement,
- deduplication,
- ordering,
- congestion control at the application layer,
- message integrity beyond what the lower layers already provide.

That simplicity is intentional. The example is meant to exercise Commonware’s communication stack rather than demonstrate a rich application protocol.

## Summary

`examples/flood/` is best understood as a distributed p2p throughput and latency probe built on top of Commonware’s authenticated discovery stack.

At the application layer, every peer just:

1. discovers other peers,
2. opens authenticated encrypted channels,
3. floods all connected peers with timestamped random messages,
4. measures receive latency,
5. exports metrics.

The interesting engineering in the example is not the application payload itself. It is the composition of Commonware modules:

- `commonware-cryptography` for identity and signatures,
- `commonware-codec` for message encoding,
- `commonware-p2p::authenticated::discovery` for peer discovery and channel routing,
- `commonware-stream::encrypted` for secure transport,
- `commonware-runtime::tokio` for execution and telemetry,
- `commonware-deployer::aws` for deployment and observability.

That makes flood a compact example of how Commonware’s networking primitives can be assembled into a real multi-region deployment, even though the application-level protocol is intentionally just "send random bytes as fast as possible and measure what arrives."
