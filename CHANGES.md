# Alto Validator Visualization Changes

## What I Researched And Found

I compared [VALIDATOR.md](/Users/dhruv/Documents/monorepo/VALIDATOR.md) against the Alto visualization in [commonware-visualization/src/data/alto/modules.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/data/alto/modules.js), [commonware-visualization/src/data/alto/pipelines.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/data/alto/pipelines.js), and [commonware-visualization/src/components/AltoVisualization.jsx](/Users/dhruv/Documents/monorepo/commonware-visualization/src/components/AltoVisualization.jsx). I then checked the Alto source in `../alto` to verify which differences were real:

- The validator really has three distinct validator-to-validator paths: consensus traffic, block dissemination, and marshal-driven repair/backfill. This is documented in [VALIDATOR.md](/Users/dhruv/Documents/monorepo/VALIDATOR.md#L324) and implemented through five channels in [validator/src/main.rs](/Users/dhruv/Documents/alto/validator/src/main.rs#L206).
- The visualization currently compresses that into a single P2P pipeline that is labeled as consensus traffic but drawn as `broadcast -> cryptography -> p2p -> cryptography -> broadcast` in [commonware-visualization/src/data/alto/pipelines.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/data/alto/pipelines.js#L1).
- Marshal is a first-class validator subsystem in both the report and the Alto engine. It stores finalized data, handles subscriptions, and serves repair/fetch traffic in [VALIDATOR.md](/Users/dhruv/Documents/monorepo/VALIDATOR.md#L89) and [chain/src/engine.rs](/Users/dhruv/Documents/alto/chain/src/engine.rs#L103). The current validator internals omit it.
- The visualization shows proposer-to-indexer traffic during `PROPOSE` in [commonware-visualization/src/components/AltoVisualization.jsx](/Users/dhruv/Documents/monorepo/commonware-visualization/src/components/AltoVisualization.jsx#L371), but the real validator only uploads on notarization and finalization events through the indexer pusher in [chain/src/indexer.rs](/Users/dhruv/Documents/alto/chain/src/indexer.rs#L119).
- The visualization draws HTTP links from every validator to the indexer in [commonware-visualization/src/components/AltoVisualization.jsx](/Users/dhruv/Documents/monorepo/commonware-visualization/src/components/AltoVisualization.jsx#L356), but deployment only enables indexer upload for a subset of validators. Local config uses only the first validator in [deploy/src/main.rs](/Users/dhruv/Documents/alto/deploy/src/main.rs#L344), and remote config selects only some validators in [deploy/src/main.rs](/Users/dhruv/Documents/alto/deploy/src/main.rs#L530).
- The consensus description in [commonware-visualization/src/data/alto/modules.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/data/alto/modules.js#L6) hard-codes `3-of-5` and the animation rotates leaders deterministically in [commonware-visualization/src/hooks/useAltoAnimation.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/hooks/useAltoAnimation.js#L28), while the actual Alto elector is VRF-based with an initial round-robin fallback in [consensus/src/simplex/elector.rs](/Users/dhruv/Documents/monorepo/consensus/src/simplex/elector.rs#L160).
- The `broadcast` module description currently says it buffers consensus messages in [commonware-visualization/src/data/alto/modules.js](/Users/dhruv/Documents/monorepo/commonware-visualization/src/data/alto/modules.js#L27), but the validator report describes it as a separate block dissemination path in [VALIDATOR.md](/Users/dhruv/Documents/monorepo/VALIDATOR.md#L269).
- The `resolver` module description is too narrow. The real path handles missing notarized/finalized data and blocks for repair and backfill, not just certificates, as described in [VALIDATOR.md](/Users/dhruv/Documents/monorepo/VALIDATOR.md#L139).
- The `codec` description overstates the concrete format details. Alto definitely uses `commonware-codec`, but the block type specifically varint-encodes the timestamp in [types/src/block.rs](/Users/dhruv/Documents/alto/types/src/block.rs#L54) rather than matching the broader “all wire and storage formats use varint compression” phrasing now shown.

## Suggestions

- Split or relabel the validator mesh pipeline. Either show separate logical overlays for `consensus`, `block broadcast`, and `repair/backfill`, or rename the current edge to something broader like `validator traffic` and add `consensus` and `resolver` to the connection-level modules.
- Add `marshal` to the validator internals, or rename the existing `resolver` chip to `marshal/backfill` so the visualization reflects the validator subsystem that actually owns persistence, subscriptions, and repair handling.
- Remove the proposer-to-indexer push during `PROPOSE`. The upload animation should happen only when representing notarization/finalization reporting, and it should reflect that seed upload happens immediately while full notarized/finalized wrappers are uploaded after marshal can supply the block body.
- Make validator-to-indexer links optional and selective instead of universal. A dashed optional edge, a different style for uploader validators, or a note that only configured validators push to the indexer would better match Alto deployment behavior.
- Generalize the consensus copy so it does not hard-code `3-of-5`. Describe it as threshold signatures over the configured validator set.
- Clarify that leader selection is VRF-based in the system model. If the animation remains deterministic for readability, label it as a visualization simplification instead of implying the live system rotates leaders round-robin.
- Rewrite the `broadcast` module description so it refers to buffered block dissemination rather than buffering consensus messages.
- Rewrite the `resolver` module description so it covers repair and backfill of missing blocks and notarized/finalized artifacts, not just certificates.
- Soften the `codec` description to avoid claiming a uniform varint-compressed format for all Alto wire and storage data.

## No Change Needed

- The runtime foundation band is directionally accurate.
- The validator storage chip is consistent with the validator report.
- The parallel verification chip is also directionally accurate for validators, indexer, and follower.

- Add a follower-internal chip for `consensus` labeled `marshal`, or add a separate `marshal` module if you want to avoid conflating follower marshal with validator `simplex::Engine`.

If you keep one edge, relabel it to something like `WS stream + HTTP repair` instead of plain `HTTP/WS`.
- Update the follower tooltip so it mentions marshal explicitly, notes that WebSocket traffic includes seeds/notarizations/finalizations, and distinguishes live streaming from HTTP repair/backfill.
- Rewrite the `parallel` module description so it says the follower uses `Sequential` on feeder/tip verification and a configurable runtime-created strategy inside marshal for resolver-path verification.
- Rewrite the `storage` module description so it says the follower persists finalized blocks and finalizations in archives that are immutable or prunable depending on configuration, instead of always calling them immutable.

### No Change Needed

- I would not add a real P2P edge to the follower. The source and docs are consistent that the follower does not maintain validator peer connections in normal operation, even though it carries some `commonware-p2p` compatibility types internally.
